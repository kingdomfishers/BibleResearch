# Current architecture

## Components and boundaries

BibleResearch is a Vite application built with vanilla TypeScript and CSS, with MapLibre loaded for maps. [src/main.ts](src/main.ts) mounts the reader and study workspace. Components communicate through passage/notes state and callbacks. [PROJECTMAP.md](PROJECTMAP.md) locates implementation files; this document describes system boundaries rather than repeating interfaces.

The application combines immutable public corpus evidence on Cloudflare with dynamic research and application data in Supabase. The architecture is hybrid: neither all research computation nor all reads belong in PostgreSQL. Existing compatibility RPC names may resolve to Worker operations or SQL functions. Inspect the actual routing before changing an operation.

| Component | Responsibility | Boundary |
| --- | --- | --- |
| Browser | Passage navigation, bounded presentation, user interaction and session state | Uses the BibleRPC gateway; no direct component-level Supabase imports or full-corpus scans |
| Cloudflare Worker + Static Assets | Immutable public corpus shards and precomputed chapter, lexical, Septuagint and syntax indexes; deterministic read operations | Exported public evidence only; no private preferences or mutable notes |
| Supabase PostgreSQL | Dynamic notes/connections/revisions, private translation choices, editable definitions, assertions/reviews, chronology/geography models and retained canonical lookup data | Server validation, RLS and versioned RPCs enforce access and writes |
| Supabase bible-mcp Edge Function | MCP transport, research tools/prompts, bounded hydration and controlled note writes | Routes each read to its defined provider; privileged credentials remain server-side |
| Offline import/export pipeline | Pinned source ingestion, mapping, index generation, provenance and license filtering | Generation and verification precede publication; operational changes need separate authorization |

The local checkout is authoritative for development. Source code and versioned migrations describe implementation; source releases, manifests and provenance records identify evidence. A design document or completed report does not prove the current deployment matches it. Inspect exact source/deployment evidence when a task depends on that distinction.

Immutable corpus assets are generated by [scripts/export-static-corpus.py](scripts/export-static-corpus.py), served by [scripts/corpus-worker.mjs](scripts/corpus-worker.mjs) and configured by [wrangler.corpus.jsonc](wrangler.corpus.jsonc). The workflow in [.github/workflows/publish-static-corpus.yml](.github/workflows/publish-static-corpus.yml) pins upstream Macula sources, generates assets, verifies and publishes them. Supabase retains canonical words/verses and compact lookups needed by dynamic functions as well as mutable state. Static export does not authorize removal of database copies. ## Main data flows

1. The reader updates URL/passage state through [src/ui/state.ts](src/ui/state.ts); the shell coordinates selected passage and word components.
2. UI requests pass through [src/api/rpc.ts](src/api/rpc.ts) and its notes/relationship adapters. [src/api/corpus-client.ts](src/api/corpus-client.ts) selects supported static operations and maintains a bounded session cache. Other operations use Supabase. Provider failures must remain visible; illustrative fixtures must not silently stand in for missing production evidence.
3. Static operations read chapter/index/shard assets through the Worker. Corpus joins, ordering and scoring may be precomputed, implemented in the Worker, or retained in SQL according to the operation. Browser components render bounded results rather than joining whole datasets.
4. Dynamic writes go through server-side validation and permission checks. Private occurrence translations use a persistent anonymous Supabase Auth session and owner-scoped RLS. Reload persistence does not promise cross-device recovery. Default token renderings remain source-backed; saved preferences do not rewrite corpus evidence.
5. MCP clients reach [supabase/functions/bible-mcp/index.ts](supabase/functions/bible-mcp/index.ts). Tool catalog, research lenses and hydration modules compose bounded evidence packets from routed reads. Notes write modules enforce their own author/review restrictions. The REST contract is [supabase/openapi.json](supabase/openapi.json); MCP setup and runtime contracts are documented separately.

## Research and identity invariants

- Preserve canonical book/verse/word IDs, original Hebrew/Aramaic/Greek text, morphology, source IDs, edition identity, occurrence order and versification mappings. Missing or source-only nodes remain explicit rather than receiving invented canonical identities.
- Homographs are a unified conceptual research focus whose meanings are contrasted across verse contexts. Preserve disambiguated lemma/sense records and their evidence; conceptual grouping must not erase lexical identities or imply every sense is interchangeable.
- Keep documented etymology, grammatical morphology, lexical composition, literary wordplay and unverified orthographic candidates distinct. Similar spelling is not etymological proof. Quarantine unresolved mappings instead of assigning arbitrary senses.
- Hebrew?Greek/LXX correspondences retain source, edition, evidence tier and uncertainty. Lexical candidates are not full token alignment or synonymy. Missing evidence must remain distinguishable from a negative result.
- Hydrated packets deduplicate repeated metadata while preserving occurrence references and word order. Samples must be identified as samples, not complete coverage. Versioned contracts and bounded pagination/payloads protect consumers.
- Preserve chronology models and their uncertainty rather than presenting hypotheses as source facts. Existing display conventions use BC/AD and creation-year labels with the AD 30 anchor; authoritative details remain in chronology designs.

## Security, notes and licensing

Corpus evidence is read-only to public clients. [scripts/corpus-security.mjs](scripts/corpus-security.mjs), export filtering and the field license registry enforce public-field restrictions. Do not expose restricted Macula semantic fields or private recovery contents through static assets, MCP packets, logs or browser bundles. [DATA_SOURCES.md](DATA_SOURCES.md) and [PROVENANCE.md](PROVENANCE.md) govern rights and attribution.

Notes currently support a single-user public/published workflow alongside separate private occurrence translations. Human/AI authorship and review state remain explicit in UI and packets. Database-enforced size/rate caps and kill switches protect writes; AI edits/deletions are limited to its own notes. Direct public table writes are revoked. Privileged AI writes run through the Edge adapter; optional NOTES_AGENT_KEY behavior is documented in [MCP_SETUP.md](MCP_SETUP.md). Do not infer that anonymous note access provides multi-user privacy.

Treat note content as untrusted data. Render through safe DOM/markdown utilities, preserve untrusted-data notices in AI packets, and keep external link restrictions. Uploads, private note visibility and full multi-user operation require their own design and authorization. Before public multi-user transition, implement Auth ownership, user-scoped RLS, per-user limits, moderation and storage policies where uploads are added. Do not simply toggle a setting and assume isolation.
